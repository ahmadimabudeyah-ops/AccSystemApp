## 2. نمط العزل متعدد المؤسسات — القرار: قاعدة مشتركة + RLS صارم

**القرار:** قاعدة بيانات واحدة لجميع المستأجرين مع `tenant_id` في كل جدول
وعزل جبري عبر Row-Level Security (مع `FORCE`)، ومفتاح الجلسة
`app.current_tenant_id` يضبطه الوسيط لكل طلب، ويفشل مغلقًا (صفر صفوف) عند غيابه.
**التبرير:** (1) كلفة تشغيلية منخفضة لسوق أردني سعر-حساس؛ (2) ترقيات مخطط
ذرية واحدة بدل N قاعدة؛ (3) تقارير مجمعة للمجموعات عبر الكيانات؛
(4) RLS على مستوى المحرك يمنع التسرب حتى مع خطأ برمجي في `WHERE`.
**بدائل مرفوضة:** قاعدة لكل مستأجر (تكلفة ترحيل وتشغيل عالية، ونسخ احتياطي
مجزأ)، ومخطط لكل مستأجر (تعقيد `search_path` وتسرب عبر الإعدادات).

## 3. طبقات التطبيق

| الطبقة | المسؤولية | أمثلة فعلية |
|---|---|---|
| Presentation | عرض HTML + REST JSON، تحقق سطحي | `app/web/*` (15 حزمة)، `app/api/v1/*` (17 حزمة) |
| Application | حالات الاستخدام، المعاملات، الأحداث | `app/services/*` (23 خدمة) |
| Domain | الكيانات والقواعد المحاسبية الخالصة | `app/models/*` + دوال التحقق |
| Infrastructure | الاتصال، الترحيلات، البذور، السجلات | `extensions.py`, `migrations/`, `scripts/` |

القاعدة: لا يستورد `web/api` من قاعدة البيانات مباشرة إلا عبر الخدمات؛
ولا تكتب أي وحدة في `journal_lines` إلا عبر `PostingService`.

## 4. الاتصال نواة ↔ وحدات: أحداث (Event-Driven)

كل حدث مالي يحمل `event_key` فريدًا `(tenant, entity, module, document, type, version)`.
المصدر (مبيعات/رواتب/أصول) يسجل الحدث ثم يستدعي النواة بنفس المعاملة؛
إعادة الإرسال تُعيد القيد الأصلي بدل التكرار (`DuplicateEventError → 200`).
لا توجد طوابير خارجية في v1 (معاملة قاعدة البيانات هي الوسيط) — تُضاف
طوابير (Redis/Celery) في المرحلة الثانية للفوترة الإلكترونية والتقارير الثقيلة.

## 5. المعاملات وACID

- كل عملية كتابة داخل معاملة واحدة (`db.session.commit` واحد).
- القيد والسطور والمفتاح واللقطات المرتبطة تُكتب ذريًا.
- القفل المتفائل عبر عمود `version` للمستندات المتنازع عليها.
- التسلسلات (الأرقام الرسمية) بقفل صف (`SELECT ... FOR UPDATE`) لمنع التكرار.
- مستويات العزل الافتراضية لـ PostgreSQL مع تجنب القفل الطويل (معاملات قصيرة).

## 6. منع الازدواج (Idempotency)

1. `event_keys(event_key UNIQUE)` + إدخال أولًا (`ON CONFLICT` ضمنيًا عبر الفحص).
2. نفس المفتاح + نفس المحتوى (بصمة `content_hash`) = إعادة نفس القيد.
3. نفس المفتاح + محتوى مختلف = `409 EVENT_CONFLICT`.
4. رأس `Idempotency-Key` في HTTP يُخزن كمفتاح الحدث.

## 7. التخزين المؤقت

لا cache للبيانات المالية في v1 (المصدر دائمًا القيود المرحلة)؛ يُسمح لاحقًا
بتخزين لقطات التقارير (`report_snapshots`) بمفتاح `(tenant, template, params, hash)`.

## 8. الطوابير

v1 متزامن؛ الطابور الوحيد منطقي وهو `einvoicing_queue` (حالات queued/sending/
accepted/rejected) لربط JoFotara لاحقًا، ومهام مجدولة للإهلاك والأعمار.

## 9. مخطط النشر (محلي الآن، سحابي لاحقًا)

## 11. معمارية الأمان

طبقات: TLS → JWT (قصير العمر) + Refresh → مطابقة مستأجر JWT/Hader (403 عند
التزوير) → RBAC لكل endpoint → RLS على كل جدول → تدقيق إلحاقي →
bcrypt للكلمات + `Is_deleted` بدل الحذف الفيزيائي. التفصيل في المخرج 7.

## 12. معمارية الأداء

فهارس `(tenant, entity, date/status)` لكل الحركات؛ BRIN للزمنيات الكبيرة؛
GIN للبحث العربي (trgm) وJSONB؛ تقسيم شهري للقيود والفواتير وسجلات التدقيق؛
ترقيم صفحات إجباري (50)؛ تجميع التقارير من اللقطات لا من المسح الحي.

## 13. قرارات معمارية (ADR مختصر)

| # | القرار | البديل المرفوض | السبب |
|---|---|---|---|
| 1 | Monolith منظّم (Flask Blueprints) | Microservices | فريق صغير وسوق أولي؛ الفصل لاحقًا عبر الأحداث |
| 2 | SSR (Jinja2+HTMX) لا SPA | React/Vue | سرعة تسليم + RTL أصلي + SEO داخلي |
| 3 | RLS إجباري لا `tenant_id` اختياري | فلترة تطبيقية فقط | الأمان لا يعتمد على انضباط المبرمج |
| 4 | القيد المرحّل خالد | تعديل بصلاحية | مبدأ تدقيقي غير قابل للتفاوض |
| 5 | PostgreSQL فقط (لا Mongo/Redis إلزامي) | تعدد المخازن | الاتساق المحاسبي أولًا |
